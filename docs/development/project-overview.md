# NextForm プロジェクト概要

> **このドキュメントの位置づけ**
> NextForm の目的・上流の実態・ロードマップ・確定した設計判断をまとめた、
> プロジェクトの基準文書。セッション開始時に最初に読む。
>
> 2026-08-02 の実環境調査に基づく。

---

## 1. プロジェクト名と目的

- **プロジェクト名**: NextForm
- **目的**: 既存の wiki エンジン [toratorawiki](http://toratora.wiki/) をフォークし、
  最新の PHP 環境への対応、セキュリティ強化、機能追加(特に Markdown 文法対応)を行う。
- **リポジトリ**: `git@github.com:nofukao/NextForm.git`
  (v0.1 完成まで private、その後 GPLv3 の OSS として公開)

## 2. 上流 (フォーク元) について

| 項目 | 内容 |
|---|---|
| 名称 | ToraToraWiki |
| バージョン | **1.3.10 (revision 1285)** |
| baseline | Git のタグ **`upstream/1.3.10`** (2022-04-24 取得の tar.gz を展開したもの) |
| 公式 | http://toratora.wiki/ |
| ライセンス | GPLv3 (`license.txt` として同梱) |
| 言語 | PHP (手続き型)、**212 ファイル / 約 21,800 行** |
| データ保存 | DB 不使用。DocumentRoot 配下にファイルとして直接保存 |
| 文法 | PukiWiki ライクな独自記法 |
| 最終更新 | 2015 年 (PHP 5 時代) |

**上流との関係**: 上流は 2015 年以降更新が止まっているため、**独立した fork として進める**。
PR は送らない。`license.txt` / `LICENSE` は、**GPLv3 の条文と上流の著作権表示は
そのまま残したうえで**、fork であることと NextForm の著作権表示・改変告知を
冒頭に書き加える (GPLv3 §5(a) が改変版に求めているもの)。
`README.md` にも fork 経緯と GPLv3 継承を明記する。

## 3. 上流ソースの実際の構造

> ⚠️ **重要**: 上流は PukiWiki レイアウト
> (`plugin/` `skin/` `wiki/` `attach/` `backup/` `cache/` `counter/` `diff/`) では
> **ない**。実物は以下のとおり。

### 3.1 tar.gz に含まれるもの (= Git で追跡する対象)

```
toratorawiki/
├── index.php          ← カスタム設定を書いて app/boot.inc を require するだけの薄いファイル
├── .htaccess          ← index.php / index.html 以外を全 deny
├── license.txt        ← GPLv3
├── app/               ← ロジック全部
│   ├── boot.inc, main.inc, setup.inc      … 起動・設定
│   ├── util.inc, page.inc, storage_file.inc … 基盤
│   ├── search.inc, search/                … 検索 (builtin 2-gram / Elasticsearch)
│   ├── handler/       … コンテンツ種別ごとの処理
│   │   ├── wiki.inc, text.inc, file.inc
│   │   ├── wiki/      … wiki_parse.inc (834行), wiki_convert.inc, wiki_lib.inc
│   │   │   └── function/  … &calendar, &calc, &table … 記法拡張 30 個超
│   │   └── file/      … file_image.inc, file_audio.inc, file_video.inc, file_binary.inc
│   ├── option/        … 画面 (search, history, admin_setup, attach … 40 個超)
│   ├── otherwiki/     … PukiWiki / @wiki からのインポータ
│   ├── theme/basic/   … テーマの**ソース** (.base.css, .function.css, html.php, setup.php)
│   ├── tool/          … CLI ツール (update_wiki, import_pukiwiki, analyze_weblog …)
│   ├── test/test      … 自前のテストハーネス (テスト 3 件のみ)
│   ├── manual/        … 組み込みマニュアル
│   └── plugin/        ← **空ディレクトリ**
└── resource/          ← js / 画像 (prototype.js, toratora.js, jscolor …)
```

### 3.2 インストーラが生成するもの (= Git で追跡しない対象)

```
storage/                ← wiki の実データ
├── page/
│   └── 546f70/head     ← ディレクトリ名は bin2hex(ページ名)。"546f70" = "Top"
│       01781508544      ← 過去版はタイムスタンプ名で同居
├── cache/              ← 2-gram 検索インデックスなど
└── setup/              ← サイト設定、認証ダイジェスト
theme/                  ← app/theme/ からビルドされた静的 CSS/JS
install-info.dat        ← インストール時の環境記録
```

- ページ本文は `*.txt` **ではない**。`storage/page/<bin2hex(名前)>/head` が現行版。
- サブページはディレクトリ名末尾の `_` で表現される
  (`storage_find_filepaths_by_prefix_recursive()` 参照)。

### 3.3 押さえておくべき既存実装

| 箇所 | 内容 |
|---|---|
| `app/search.inc` | 検索は **2-gram インデックス**方式。`storage/cache/` にインデックスを持つ。素朴な全文スキャンではない |
| `app/search/elasticsearch.inc` | **外部検索エンジンへの差し替え機構が既にある**。`SEARCH_ENGINE` 定数で切り替え |
| `app/option/search_index.inc` | 管理画面「Rebuild search index」。インデックス再構築 |
| `app/storage_file.inc` の `storage_page_find()` | 全ディレクトリ走査 + `filemtime()` + `usort()`。遅い原因と見ていたが、1372 ページで 0.13 秒。**実測では問題になっていない** (§6 の v0.3 参照) |
| `app/setup.inc` | `TIME_FORMAT` / `DATE_FORMAT` は管理画面から変更可能な **strftime 形式**の文字列 |
| `app/language.inc` | `l()` によるメッセージ変換。`setlocale()` は**一度も呼ばれない** |
| `app/test/test` | 自前テストハーネス。`page_path` / `wiki_tokens_is_whitespace` / `template_get_placeholders` の 3 件のみ |


**配布パッケージの作成**:
```bash
./deploy/scripts/make-dist.sh          # HEAD から
./deploy/scripts/make-dist.sh v0.1     # tag から
```
上流と同じ「展開してブラウザで開けばインストーラが動く」形式になる。

> `tar zcf NextForm.tar.gz NextForm/` としてはいけない。`.gitignore` で
> 無視しているだけの生成物 (`theme/` `storage/` `install-info.dat`) や
> 作業中のファイルが紛れ込む。実際、開発中に `php -S` で動かした残骸の
> `theme/` が作業ツリーに残っていた。`make-dist.sh` は `git archive` で
> **追跡されているファイルだけ**を固め、生成物が混ざっていないか検査もする。

## 5. 上流の参照インスタンス

素の ToraToraWiki 1.3.10 を別のパスに展開し、**上流の振る舞いの基準**として
温存しておくと判断が早い。作り方は [setup.md](setup.md) §4。

- 参照インスタンスは**変更しない**。比較の基準として意味がある
- 素の上流は **PHP 8 では起動しない** (`get_magic_quotes_gpc()` で Fatal error)。
  起動させるには `app/util.inc` のその 1 行と `app/option/search.inc` の
  `each()` を除去する必要がある。PHP 8 で削除済みの関数はこの 2 箇所だけ
- インストールしただけのインスタンスはページが 2 件しかないので、性能計測には
  使えない。`deploy/scripts/gen-pages.php --count` で別途生成する

差分を見るだけなら Git で足りる。

```bash
git diff upstream/1.3.10 HEAD -- NextForm/app/
```

#### PHP 8.4 を対象外にした理由 (2026-08-02)

当初は 8.3・8.4 の両方で動作確認する方針だったが、**8.3 のみ**に変更した。
AlmaLinux 10 の AppStream は 8.3 までで、8.4 には remi の追加が必要になるが、
コードを照合した結果それに見合う効果が無いと判断した。

| 8.4 の主な非推奨・変更 | 該当 |
|---|---|
| 暗黙の nullable 引数 (`Foo $x = null` → `?Foo`) — 8.4 最大の非互換 | ❌ このコードには**型宣言が 1 つも無い** |
| `E_STRICT` の非推奨 | ❌ 未使用 |
| `session.sid_length` 等の非推奨 | ❌ 未使用 |
| ext/dom | ⚠️ `DOMDocument` / `DOMXPath` を使用中。ただし 8.4 の変更は `Dom\HTMLDocument` の**追加**で、従来 API に非推奨は無い |
| `strftime()` | ✅ 8.4 でも非推奨のまま (削除は 9)。しかも既に呼んでいない |

v0.1 で修正した内容 (null を内部関数に渡す非推奨、参照渡しコールバック) は
8.1〜8.4 で共通の指摘であり、**PHP 9 で TypeError / 関数削除になる本当の崖**は
既に越えている。8.4 で新たに出る警告は無い見込み。

### v0.1.1 — 既存サイトからのアップグレード経路 ✅ 完了 (2026-08-03)

v0.1 の価値は「2015 年で止まった既存サイトを PHP 8 で動かす」ことにあるのに、
既存サイトを移行する手段が無かった。公開前に塞いだ。

| 成果物 | 内容 |
|---|---|
| `NextForm/app/tool/upgrade` | アップグレードスクリプト。配布物に同梱される |
| `docs/upgrade-guide.md` | 手作業の手順書。**正本はこちら**。`make-dist.sh` がリリース時に `NextForm/UPGRADE.md` としてコピーする |
| `tests/upgrade.sh` | tora2 の複製に対して両方の経路を実際に走らせる |

**このタイミングでやった理由**: v0.1 時点の変更は `app/` に閉じており、
`index.php` / `.htaccess` / `resource/` / `license.txt` とページの保存形式は
上流と同一。アップグレードは「コードを差し替えてテーマを作り直す」だけで済む。
v0.3 で `storage_page_find()` の性能改善に入るとインデックス形式が変わりうるので、
データ移行が絡む前に枠組みを作っておく。

#### 実装上の判断

- **消さない。** 配布物に無いファイルが `app/` にあっても削除せず報告する。
  利用者のプラグイン (`app/plugin/`) や独自テーマ (`app/theme/<名前>/`) を
  巻き添えにしないため。「知らないものは消さない」を原則とする
- **静的テーマの再生成をスクリプトに含める。** `app/theme/` はソースで
  `theme/` が生成物。再生成しないと見た目の修正が一切反映されない。
  手動では最も忘れられやすい工程
- **所有者は書き換える前に控えて復元する。** root で実行すると新しいファイルが
  root 所有になり、web サーバから読めなくなる
- **手順書もテストから実行する。** 実際これで 2 件のずれが見つかった。
  手作業では所有者を戻してからテーマを再生成しないと `update_wiki` の
  所有者チェックに引っかかること、`diff` の見出しがロケールで日本語になり
  `grep '^Only in app'` に引っかからないこと

### v0.3.0 — 検索の信頼性修正 ✅ 完了 (2026-08-17 リリース)

2026-08-14〜17 に調査した。**当初の見立ては 2 つとも外れていた**。

#### 分かったこと

| 当初の見立て | 実測 |
|---|---|
| 100 ページ超で検索が正常に行えない | **索引の破壊**で起きる。ページ数とは無関係 |
| ページ数が増えると `&recent(20)` が 10 秒以上 | **再現せず**。1372 ページで `option=allpage` 0.13 秒 |

- **検索が壊れる本体は `search_index_add()` の全上書き**。索引ファイルを
  読めなかったとき、それを空とみなして書き戻すため、ページを 1 件保存しただけで
  そのファイルの全ページが消える。1077 ページの検証で **1062 件が一度に消えた**。
  エラーは出ず、特定の語だけ 0 件になる。再構築でしか直らない
- 索引の差分更新そのものは正しい(編集 9 パターン / 削除 4 パターンで一致)。
  問題は**一度ずれると自己修復しないこと**。差分は「旧本文と新本文」から計算され、
  索引の中身は確認されない
- **検索の速度はページ数に線形**だが緩やか。候補 1 件あたり 1.4〜2.4ms
  (候補ページごとに `wiki_texts()` でフルパースするため)。
  1372 ページの実サイトで最悪 1.6 秒。**当面は問題にならない**
- **「表示が遅い」の正体は外部取得**だった。ToraToraWiki 1.3.6 の実インスタンスで
  全 1372 ページを巡回したところ平均 0.038 秒、1 秒超は 1 ページだけで、
  それが `&calendar` の Google カレンダー取得で **21.76 秒**。
  取得先は Google が 2014 年頃に廃止した GData API で、タイムアウト指定が無い。
  `WIKI_CALENDAR_RULES_DEFAULT` に既定のカレンダー ID が入っているため、
  カレンダーを指定していないページでも発生する。
  1.3.10 は `GOOGLE_API_KEY` 未設定なら取りに行かないので実質回避されている
- 上流 1.3.6 では `?option=search&query=X&top=1` が `each()` で **Fatal (HTTP 500)**。
  NextForm は v0.1 で修正済み
- 未ログインだと検索が**黙って 0 件**になる(`auth_has_permission` で候補が落ちる)。
  仕様か不具合かは未判断

#### やったこと

| 内容 | 効果 |
|---|---|
| 読めない索引ファイルを上書きしなくなった | 1 回の保存で 1000 ページ分が消える経路を塞いだ |

#### 見送った項目 (2026-08-17 判断)

- **索引更新の排他制御**: 引き金は「同時に別のページを保存すること」で、
  再構築の頻度とは無関係。単独〜数人の運用では発生しない。
  被害もその保存で新しく書いた語だけに限られる。
  `flock` は `app/` に 1 箇所も無く、`storage_cache_create()` が
  一時ファイル + `rename` で書くため、対象ファイルへの `flock` では守れない。
  別途ロックファイルの仕組みが要る
- **再構築の完了マーカー**: 差し替え方式にしたことで**不要になった**。

#### 性能改善を v0.4 に送った理由 (2026-08-17)

当初 v0.3 は「検索バグ修正と**性能改善**」だったが、性能は実測の結果**急ぐ必要が
無かった**ため切り離した。1372 ページの実サイトで最悪 1.6 秒、候補 1 件あたり
1.4〜2.4ms。当初の見立て「100 ページで 10 秒以上」は再現していない。

一方で索引が壊れる不具合はデータが失われる性質のもので、**版数を上げないと
利用者に届かない** (アップグレードツールが同じ版数を拒否する)。
方式選定から始まる案件のためにデータ修正の配布を止めるのは順序が逆と判断した。

#### 再構築をいつ行うか

定期的に行う必要は無い。索引は保存・削除のたびに増分で維持されており、
数ヶ月再構築していないサイトでも整合していた。必要になるのは:

- `app/tool/search_index_check` が異常を報告したとき
- **PHP や wiki 本体を上げたとき・サイトを移設したとき。**
  本文の抽出結果が環境で変わりうる。実際、古い環境で作られた索引を持つ
  1372 ページのサイトでは 1201 ページで ngram が欠けていた
  (現在のコードで再構築済みのサイトでは 2 件)
- `storage/cache/` を手で消したとき。**このディレクトリで自動再生成されないのは
  検索インデックスだけ**なので、「キャッシュだから消してよい」と扱うと検索が死ぬ

#### 上流由来の壊れた登録 (2026-08-18 に修正)

`handle()` と `option()` が登録表のキーを全部「URL から呼べる action」として
扱っていたため、次の 3 件が 500 になっていた。

| 登録 | 中身 | 画面から使われているか |
|---|---|---|
| `$OPTIONS['listedit']['insert']` | `listedit_insert()` が**存在しない** | されていない。JS が送るのは `action=write` だけ |
| `$OPTIONS['history']['diff']` | `history_diff()` が**存在しない** | されていない。版の比較は `option=compare` が担う |
| `$HANDLERS['wiki']['normalize']` | 実体はある。`handle()` が `($page, $dom)` で呼ぶが、`wiki_normalize(&$page, $text)` の第 2 引数は文字列 | **`handler_function()` 経由では使われている** (insert / replace / listedit / templateedit)。登録は消せない |

`$HANDLERS['wiki']['texts']` も同じ形。500 にはならないが本文が空のページを返していた。
`handler_function()` 経由で検索が使っているので、これも登録は消せない。

実害は小さかった (`display_errors` が Off なので応答は 0 バイト、状態も変わらない)
が、`function_exists()` の確認と内部部品の除外で一括して塞いだ。

#### 検索の性能改善

実測 (nm_old / 1372 ページ / PHP 8.3) で、**検索時間の 92〜95% が `wiki_texts()`**
だった。候補ページごとに字句解析 → 構文解析 → DOM 構築をしており、
`nocache` 指定でキャッシュも効いていない。索引の引き込みは 0.1〜2.9ms で
無視できる。**遅いのは索引ではなく、そのあとの本文の再パース。**

| 検索語 | 候補 | 索引 | `page_read` | `wiki_texts` | 合計 |
|---|---|---|---|---|---|
| ネットワーク | 74 | 1.1ms | 3.7ms | 135.6ms (92%) | 146.6ms |
| 設定 | 256 | 0.1ms | 15.9ms | 471.9ms (93%) | 507.9ms |
| の | 564 | 2.9ms | 31.9ms | 815.1ms (93%) | 880.2ms |
| a (最悪) | 1167 | 2.2ms | 403.4ms | 942.7ms (93%) | 1011.7ms |

**方式: 抽出結果をページごとに `storage/cache/` へ持つ** (キー `search_texts`)。
試作しての実測:

試作時の見積り (40x など) は**本文抽出の部分だけ**を測ったもので、検索全体では
そこまで伸びない。実装後に検索全体で測り直した値が下表 (同じサイト、
語ごとにキャッシュを消してから 1 回目 → 2 回目):

| 検索語 | 候補 | 1 回目 | 2 回目 | 倍率 |
|---|---|---|---|---|
| ネットワーク | 73 | 154ms | 11ms | 14x |
| 設定 | 256 | 541ms | 36ms | 15x |
| の | 564 | 962ms | 69ms | 13x |
| a (最悪) | 1167 | 1155ms | 117ms | 9x |

ブラウザから見た応答時間 (認証あり、描画込み) は 設定 が 0.56 秒 → 0.05 秒、
の が 0.48 秒 → 0.08 秒。

**直したあとは、残り時間の中身が変わる。** 256 件の候補で 31.5ms の内訳は
照合・スニペット生成・採点が 20.0ms (63%)、`page_read` が 6.1ms、
キャッシュの読み出しが 5.4ms、権限確認が 0.1ms。
再パースが消えた分、次に効くのは**スニペット生成**になる (v0.5 以降の課題)。

設計上の要点:

- **有効性の判定はページの mtime だけ**で行う
  (`cache_serialized_get($pagename, 'search_texts', $page['mtime'] + 1)`)。
  `page_read()` が入れた値をそのまま使うので追加の I/O はゼロ。
  `export.inc` が既に同じ流儀
- md5(本文) の指紋方式は**却下**。判定のために全候補の本文を読み直すことになり、
  試作で最悪ケースが 1011ms → **3833ms と現状より遅くなった**
- 無効化は自動。`page_write()` / `page_delete()` が先頭で
  `cache_delete($page['name'])` を呼び、そのページのキャッシュを全部消す
- **書き込むのは検索の経路だけ。`search_page_ngram()` からは書かない。**
  `page_write()` は `cache_delete()` の**あと**に旧本文の ngram を計算するため、
  そこで書くと古い内容が残る
- 外れても壊れない。見つからない・読めない・古い、のどれでも再計算するだけ。
  **間違えると結果が変わる検索インデックスとは性質が違う**
- 代償: storage は 1 ページ約 2.5KB (1372 ページで約 3.4MB)。初回検索は
  約 17% 遅い。再構築は速くならない (索引の書き出しが支配的)
- 「索引に本文を持たせる」案は**却下**。索引ファイルは保存のたびに全体を
  書き戻すので、v0.3 で直した壊れやすい部分に負荷をかける

実装は `search_page_texts_cached()` (`app/search.inc`)。素の
`search_page_texts()` は残してあり、**索引を作る `search_page_ngram()` は
そちらを使い続ける**。`page_write()` は `cache_delete()` のあとに旧本文の
ngram を計算するため、索引側からキャッシュを書くと古い内容が残ってしまう。
`tests/search-cache.sh` がこの 1 点も検査している。

### v0.4.1 — セキュリティの積み残し ✅ 完了 (2026-08-18 リリース)

v0.4.0 の監査で残した項目を 1 つの版でまとめて片付け、v0.5 以降の
オリジナルな課題に進む。**性能改善はここでいったん完了扱いとし、
問題が生じたら個別に対応する。**

#### A. `&link()` の URI 判定を前方一致にする

`WIKI_URI_REGEX` がアンカーされておらず、一致すると**値全体**を `href` にする
(`&link(abchttp://example.com/);` → `href="abchttp://example.com/"`)。
`javascript:` は `:` がパラメータ解析で落ちるため**注入できなかった**
(複数パターンで実測)。実害は確認できていないが構造として脆い。

**定数そのものは変えてはいけない。** 同じ定数が 3 か所で違う目的に使われている。

| 使用箇所 | 目的 | アンカーしてよいか |
|---|---|---|
| `handler/wiki.inc:26` | 字句解析のトークン定義 (本文中の URL を拾う) | **不可**。自動リンクが壊れる |
| `option/insert.inc:84` | 投稿に URL が含まれるかの検査 (スパム対策) | **不可**。素通しになる |
| `handler/wiki/function/wiki_link.inc:63` | 値全体が URL かの**検証** | **ここだけ**行う |

→ 定数は据え置き、`wiki_link.inc` の検証だけを前方一致 + スキーム許可リストにする。

#### B. ダイジェスト認証の realm をサイトごとにする

保存されるのは `md5(利用者名:'User login':パスワード)`。realm が全サイト共通の
固定値なので**同じ事前計算表が全 NextForm サイトに通用する**。

realm は 5 か所すべてが定数を読むだけで、パスワード設定画面の JS にも PHP から
渡している (`option/password.inc` `option/admin_user_client.inc`) ため、
値を差し替えれば全体が追随する。**技術的には安価。**

**移行はできない。** `HA1` は realm から作られ、認証時に平文は届かないので、
サーバー側でダイジェストを作り直す方法が原理的に無い。realm を変えると
保存済みのダイジェストは全部無効になる。

→ **新規インストールだけサイト固有の realm を使い、既存サイトは
`'User login'` のままにする** (2026-08-18 決定)。既存サイトは何も壊れない。

#### C. コードツリーの書き込み権限 → **コードでは直さない**

v0.4.0 の監査で「インストール後も `index.php` が Web サーバから書けるので
読み取り専用にしたい」と書いたが、**その対策では意味がないことが分かった。**

```
drwxr-xr-x apache apache  app/
drwxr-xr-x apache apache  app/plugin/    ← *.inc が main.inc:34 で無条件に require される
-rw-r--r-- apache apache  index.php
```

`app/plugin/` も Web サーバから書けるので、`index.php` だけ読み取り専用に
しても攻撃者はそちらに置くだけ。ツリー全体が書けるのはアップグレード
ツールの設計上そうなっている。

→ 配置の話として `docs/installation.md` に書き、`?option=admin_info` で
現状を知らせる。**強制はしない** (`index.php` は利用者が独自の `define()` を
書く場所であり、読み取り専用にすると文書化済みの手順を塞ぐ)。

#### 見送るもの

- **スニペット生成の性能。** 性能改善は v0.4.0 で完了扱い (2026-08-18 決定)
- **SSRF** (`&include_uri` / `getimagesize()`)。書き込み権限が要るうえ、

### v0.6 — Markdown 文法対応 (2026-08-19 に方針決定)

**ページ種別に `markdown` を追加する。** 種別の選択肢は `$HANDLERS` のキーから
自動生成される (`handle.inc`) ので、ハンドラを 1 つ登録すれば新規作成の
セレクタにも `?option=newpage` にも出る。`app/handler/text.inc` (138 行) が
完結したハンドラの見本になる。種別は `meta['type']` に保存され、
**既存ページの種別は変えられない** (現状の仕様を維持)。

| 決めたこと | 内容 |
|---|---|
| 種別名 | `markdown` (略さない。`meta['type']` に焼き付いて後から変えられないため) |
| 変換 | **league/commonmark 2.10 を同梱** (`app/vendor/`)。利用者に composer は要求しない |
| 生 HTML | **既定はエスケープ** (`html_input: escape`)。`MARKDOWN_ALLOW_HTML` で解禁できる |
| 拡張 | GFM 一式 (表・打ち消し・タスクリスト・自動リンク・脚注) + `[[リンク]]` + 見出しアンカー + 画像/子ページ解決 + フロントマター |
| フロントマター | **自前の最小パーサを注入する。`symfony/yaml` は同梱しない** |
| CSS | `common/style/.markdown.css` を新設し、4 テーマで共有 |
| 数式 `$...$` | **見送り**。commonmark の機能ではなく、既存の `WIKI_MATH_*` は platex を外部起動する古い作り。TeX 対応の作り直しごと将来の課題 |

実装の手順:

1. `chore/vendor-commonmark` — 同梱と憲法の注記 (**済**)
2. `feat/markdown-handler` — 最小のハンドラ (**済**)
3. `feat/markdown-wikilink` — `[[ページ名]]` (**済**)
4. `feat/markdown-anchor` — 見出し id と目次 (**済**)
5. `feat/markdown-style` — `.markdown.css` (**済**)
6. `docs/markdown` — 組み込みマニュアル (**済**)

実装して分かったこと:

- **`$HANDLERS` に登録するだけで種別の選択肢に出る。** 画面側の追加は不要だった
- **`texts` は「変換してから文字を取り出す」。** 記法を正規表現で落とす方式にしなかったので、
  表のセルや脚注の中身まで検索に載り、フロントマターは載らない
- **`[[...]]` のリンクは `dom_append_page_link()` に作らせる。** 未読・自分自身・
  存在しないページの印・`data-link-pagename` を二重に実装すると必ず取りこぼす
- **見出しの id は `page_get_section_id()`。** wiki と同じ規則なので、
  `[[ページ名#見出し]]` が種別をまたいで同じ場所に届く
- **CSS には穴が 2 つあった。** `h2` 以降に当たる規則が 1 つも無い (wiki の見出しは
  常に `h1`)、`blockquote` が wiki 用に `white-space: pre`。`.markdown.css` で埋めた
- **組み込みマニュアルの記法に注意。** 本文中のバッククォートは `manual_parse()` が
  PHP として `eval` する (`$bq$` と書く)。記号をそのまま出すのは `&` 1 つの前置で、
  `&&` は「`&` そのもの」。表のセルの中の `|` は `""` で囲んでも守れず `&|` が要る

決めた小さなこと:

- **`normalize` は本文をそのまま返す**。持たないと `insert` / `replace` /
  `listedit` / `templateedit` の 4 画面が Markdown ページで動かない
- **チートシート (`?option=helper`) は Markdown ページでは出さない**。
  中身が wiki 記法の早見表なので、出すと誤解を招く。Markdown 版は後続で
- `EXPORT_DEFAULT_TEMPLATE_MARKDOWN` を `WIKI` と同じ内容で追加する

将来の課題 (v0.6 ではやらない):

- **インストーラの導入**。`composer install` で最新のライブラリを取る方式は、
  シェルも外向き通信も無い設置先を切り捨てるうえ、サイトごとに版がばらつく。
  同梱を既定に保ったまま、`app/tool/update_vendor` や slim 版配布を足す形にする
- 簡易エディタなどの編集支援、既存の wiki ページ → Markdown 変換
  (変換には「種別変更」の口が要る)
- TeX / 数式表示の作り直し

### v0.7 — マニュアルの組み込み化 (2026-08-20 に方針決定)

上流から引き継いだマニュアルは、管理者が `?option=admin_manual` で
**一般ページとして焼き付ける**仕組みだった。焼き付け先が `storage/` なので
アップグレードの対象外になり、古いマニュアルが残り続ける。アンロックすれば
編集もできる。そもそも押し忘れると、サイトメニューの「マニュアル」が
GitHub に飛ぶだけになる。

焼き付けをやめ、`MANUAL_PAGENAME` 以下を**実体を持たない読み取り専用の
仮想ページ**にした。正本は `app/` のソース 1 つだけになり、
アップグレードで `app/` が入れ替わればマニュアルも新しくなる。

分かったこと:

- **正本はもともと `app/` にあった。** `manual_parse()` が
  `manual/manual-*.txt`・`setup.inc`・`handler/wiki/function/*.inc`・
  `plugin/*.inc` の注釈から組み立てる。`admin_manual` はその写しを
  storage に作るだけの操作だった。実行時解決の前例も既にあり、
  `?option=helper` (チートシート) はページを介さず毎回組み立てていた
- **`page_is_exists()` を直せば `[[...]]` が生きる。** 未存在の印も
  `data-link-pagename` も `dom_append_page_link()` 1 箇所が付けている
  ([dom.inc](../../NextForm/app/dom.inc))。門番は既存の
  `page_is_system_page()` の前方一致で足りる
- **再入に注意が要る。** 索引を作る `search_page_ngram()` は本文を変換し、
  その途中で `page_is_exists()` を呼んで戻ってくる。ページ名の集合が
  確定した時点でメモへ入れておかないと無限に再入する
- **再構築と整合検査は同じ一覧を見なければならない。** 別々に組み立てて
  いたので、片方にマニュアルを足した時点でもう片方が「索引にあるのに
  実在しない」と報告した。`search_index_target_pages()` に集約した
- **廃止した画面のファイルは配布物に残す。** アップグレードツールは
  「配布物に無いファイルは消さない」方針なので、消すと古い
  `admin_manual.inc` が残り、もう無い `manual_build()` を呼んで Fatal error
  になる。跡地の画面で上書きするのが確実

作業中に見つけて直した別の問題:

- **`wiki_normalize()` が取り込んだページの表を自分の本文に当てていた。**
  `//table[@data-twp]` を文書全体から拾うので、`&include` で取り込んだ
  ページに表があると、その位置を自分の本文に当てて `substr()` が空を返し、
  `Uninitialized string offset 0` になる。正規化は保存のときにも走るので、
  **表を含むページを `&include` している普通のページを保存しても踏めた**
  (実測で警告 27 件)。マニュアル固有ではなく上流から続く不具合。
  取り込んだ中身は `page_handle()` が `section[@data-pagename]` で包むので、
  XPath に `not(ancestor::section[@data-pagename])` を足して除いた。
  `substr()` が空を返す場合の判定も足した。
  `tests/dispatch.sh` に、取り込んだページを整形しても警告が出ないことと、
  自分の表は揃うことの検査を足した

## 8. ロックの仕様 (2026-08-03 に調査、不具合ではない)

「ロック中のページを編集できてしまう」との報告を受けて実測した結果、
**上流の設計どおり**であることを確認した。修正はしていない。

| 利用者 | ロック中のページ | 実測 |
|---|---|---|
| 管理者 (`admin` 権限) | **編集できる**。緑の通知「このページはロックされています．」が出る | 設計どおり |
| ロックした本人 (`lock` 権限) | 編集できる | 設計どおり |
| それ以外 (`write` 権限のみ) | **編集できない**。赤いエラーが出て送信ボタンも無効。サーバー側でも `page_write()` が拒否 | 保護は効いている |

- 判定は `app/lock.inc` の `lock_has_permission()`。`admin` 権限があれば無条件に true
- `app/lock.inc` の `lock_warn()` が、権限ありなら `message_notice`(緑)、
  権限なしなら `message_error`(赤)を出し分けている
- 管理者が編集して保存しても**ロック状態は維持される**(実測で確認)
- PukiWiki の「凍結」と同じ考え方。管理者まで締め出すと解除できなくなるため

> 「ロックしたら管理者も編集できない」挙動に変えたい場合は、
> `lock_has_permission()` から `admin` の特例を外し、
> 管理者はいったん解除してから編集する運用にする。
> セキュリティモデルの変更になるため、必要になった時点で判断する。
