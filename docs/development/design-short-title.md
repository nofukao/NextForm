## 1. 何を作るか

依頼元のページは、本文が次の 2 行だけの Wiki 記法のページ。子ページ `日記/YYYY-MM-DD` (Markdown) を
毎日 AI が書いている。

```
&calendar
&pages([[日記/]],reverse,type=!file)
```

困っていること:

1. カレンダーのセルに各日のページの目次 (見出しの一覧) が出る。長くて見づらい。
2. `&pages` の一覧にはタイトルしか出ない。何をした日かは、ページを開かないと分からない。

作るもの (3 つ):

| # | もの | 書き方 (案) |
|---|---|---|
| 1 | ページのメタ情報に**短いタイトル**を置く | Markdown: フロントマターの `short_title:` / Wiki: `&title(short){…}` / メタ情報の画面に入力欄 |
| 2 | カレンダーのセルにタイトルを出す形式 | `&calendar(show=title)`。短いタイトル → タイトル → (どちらも無ければ) 今の目次 |
| 3 | `&pages` の各項目に、閉じた折りたたみで目次を出す形式 | `&pages([[日記/]],reverse,type=!file,show=toc,each=31)` |

依頼元で決まっていること (変えない):

- 日付は文字列で削らない。書き手が日付を除いた短いタイトルを別に書く (Hugo の `linkTitle` と同じ考え)。
- キーの名前は `short_title`。依頼元は 2026-11-07 から既にこの名前で書いている。
  **名前を変えるなら、出す前に依頼元に知らせる** (変えない案にした)。
- カレンダーの既定は今のまま (目次)。
- `&pages` の項目は「タイトル (ページへのリンク。日付つきのまま)」と、その下に「閉じた折りたたみ
  (中身は目次)」。JavaScript を使わない素の `<details><summary>`。

## 2. 調べてわかったこと

- **タイトルの流れ。** 本文がタイトルを決める (§7「題名とタグの正」)。保存のとき、種別の
  `normalize` が本文からタイトルを取って `$page['title']` に入れ、`page_write()` がそれを
  `meta['title']` に書く。空文字は「消す」。Markdown は `markdown_normalize()` →
  `markdown_apply_front_matter()` → `markdown_set_title()`、Wiki は `wiki_normalize()` が本文を
  変換し、`wiki_operator_title()` が `$page['title']` を立てる。立たなければ空文字にして消す。
- **フロントマターの読み取りは自前の最小のもの** (`handler/markdown/front_matter.inc`)。
  `key: value` を拾うだけで、`short_title:` は今も読まれているが使われていない (依頼の書くとおり害は無い)。
  値の両端の引用符は落とす。
- **メタ情報の画面** (`option/meta.inc`) は、本文がタイトルを決めているページでは入力を使わない
  (`meta_write()` が表示の経路を走らせ、`title_dom` が立てば入力を使わない)。種別 wiki と markdown では
  入力欄の横に「本文の保存で上書きされる」と出す。
- **カレンダー** (`wiki_calendar.inc`)。日のページがあれば `page_read()` して
  `handle($page, $dd, 'summary')` で目次を `<dd>` に出す。月の表示でも前後の月の日を描くので、
  **目次を作るのは最大 42 セル** (6 週)。小さい画面とサイドバーでは CSS がこの `<dd>` を隠して「...」を出し、
  `nextform.js` の `calendarHelperSetup()` がセルを押したときに `<dd>` を浮かせて見せる。
  つまり**小さい画面とサイドバーでも、押せば今は目次が出る**。
- **`&pages`** (`wiki_pages.inc` → `pagelist.inc`)。`show=` で形 (list / tree / table / contents / date) を
  選ぶ。`pagelist_apply_rules()` は全件を `page_read()` する (meta だけ。本文は描かない)。`each=` を
  付けると、描くのはその件数だけ (`array_slice` の後で描く)。**`&datepages` と `&popularpages` も
  同じ引数の読み方 (`wiki_operator_pages_parse_parameters()`) と同じ描き方を使う。**
- **目次は種別ごとの `summary`。** Markdown は `markdown_summary()` (項目は見出しへのリンク)。Wiki は
  `wiki_summary()` で、`$page['args']['summarize_link']` を立てたときだけ項目がリンクになる
  (ツールの「目次」はそうしている。カレンダーは立てていない)。見出しが無いと、どちらも書き出しの
  1 語 (文) を文字で出す。text は書き出しの 1 語、file は埋め込み (画像など)。
  `handle()` を通すと、そのページを「読んだ」と記録する (`USER_HISTORY_UNREAD` の未読の印が消える)。
- **重さ (実測)。** 依頼元の日記と同じ形の Markdown (228 行、`##` が 10 個、表と箇条書き) を、同梱の CommonMark で
  変換して DOM に入れるだけで **1 ページ 13.7 ms**。目次を作るには毎回これが要る。
  - 今のカレンダーは 1 か月で最大 42 ページ分の目次を作っている (約 0.6 秒)。
  - `&pages` で全件に目次を付けると、1 年 (365 ページ) で**約 5 秒**、3 年で約 15 秒。
  - **Wiki のページは保存のときにも同じだけかかる。** `wiki_normalize()` は表の桁揃えのために本文を
    1 度変換するので、`&pages` も描かれる。サイド・`&include` に置いても同じだけ走る。
- **既にあるページの meta は、次の保存まで変わらない。** タイトルの取り方を変えたときも
  (§7「Markdown の題名と先頭の #」)、`meta['title']` は次の保存から変わる、とした。
  依頼元が 2026-11-06 以降に `short_title:` を書いたページも、NextForm を上げただけでは
  `meta['short_title']` が無い。
- **ゴールデンマスターのカレンダーには日のページが無い。** `GoldenMaster/Calendar` の表は空のセルだけで、
  目次を出す分岐 (今回変えるところ) の出力は固定されていない。

## 3. 設計

### 3.1 短いタイトル (メタ情報 `short_title`)

**持ち方。** `meta['short_title']`。タイトルと同じく、本文に書く場所がある種別 (wiki・markdown) では
**本文が正**。保存の経路で `normalize` が本文から取り、`$page['short_title']` に入れる。`page_write()` が
`meta['title']` の隣で `meta['short_title']` に書く。**空文字は「消す」** (タイトルと同じ約束)。

**Markdown。** フロントマターの `short_title:`。タイトルを `title:` で書いても、本文の先頭の `#` で
書いても、`short_title:` はそれとは別に読む (`markdown_front_matter_short_title()` を
`markdown_front_matter_title()` の隣に置く。並び (配列) で書かれた値は使わない。これも同じ)。

- 保存の経路では、書いていなければ空文字 (= 消す)。
- 表示の経路では、**書いてあるときだけ** `$page['short_title']` を立てる (空文字は立てない。
  `markdown_set_title()` と同じ形)。メタ情報の画面が「本文が決めているか」を `isset` で見るため。

```markdown
---
title: 2026-11-06（金）カレンダーの手直しと検索の整理
short_title: カレンダーの手直しと検索の整理
---
```

**Wiki 記法。** `&title` に引数 `short` を足す。

```
&title(short){カレンダーの手直しと検索の整理}
&title{2026-11-06（金）カレンダーの手直しと検索の整理}
```

- `&title(short)` はタイトル (`$page['title']`・ページの見出し) には触らず、`$page['short_title']` だけを
  立てる。複数あれば最後のものが勝つ (`&title` と同じ)。`show` と一緒に書けば本文にも出る。
- `wiki_normalize()` は `&title` と同じく、変換の前に `$page['short_title']` を落とし、本文に
  `&title(short)` が無ければ空文字にして消す。
- **マニュアルの例は `&title(short)` を先に書く。** 古い版 (`short` を知らない) では両方がタイトルとして
  読まれ、後に書いたほうが勝つ。先に書いておけば、古い版でもタイトルは長いほうのまま。
- **別の関数 (`&shorttitle{}`) にしなかった理由:** マニュアルの 1 ページ (`&title`) に並べて書けて、
  「本文が正」の約束もそこで 1 度説明すれば済む。依頼の例にも挙がっていた。

**メタ情報の画面。** 「タイトル」の下に「短いタイトル」の入力欄を置く。扱いはタイトルと同じにする:

- 本文が短いタイトルを決めているページでは、入力を使わない。
- 種別 wiki と markdown では、欄の横に「本文の `&title(short)` / フロントマターの `short_title:` で
  上書きされます」と出す。
- 本文に書く場所が無い種別 (text・file) では、ここで付けた値が残る。空にして保存すると消える
  (`$page['short_title'] = ''` を渡す。meta を直に落とさない)。

**検索の索引には入れない。** ふつうは日付を除いたタイトルなので、タイトル (索引に入っている) で
もう当たる。入れると、索引の作り方・検査の道具 (`search_index_check`)・Elasticsearch の項目と、
直すところが増える。タイトルと違う語を短いタイトルに書いた場合だけ、その語で当たらない (マニュアルに書く)。

**ほかの経路。**

| 経路 | どうするか |
|---|---|
| 「この版に戻す」(`page_restore()`) | タイトルと同じ。最初に `$page['short_title']` を落とし、`normalize` が本文から取らなければ、その版の meta から戻す |
| Wiki 記法 → Markdown の変換 (`wiki_markdown.inc`) | `&title(short){X}` をフロントマターの `short_title: X` にする。タグがあれば同じフロントマターに並べる。本文に無ければ meta の値を写す (タイトルと同じく、見えているものを保つ)。値の空白・改行は 1 つの空白に詰める。今は `&title` として扱われ、タイトルを上書きしてしまう |
| `&meta(short_title)` (`wiki_meta.inc`) | 出してよい項目に足す (`title` と同じ) |
| 版の比較 (`option/compare.inc`) | メタ情報の違いの表に「短いタイトル」の名前を付ける (meta は全部比べているので、名前を足すだけ) |
| 名前の変更・クローン | 変えない (名前の変更は meta ごと移る。クローンは本文から取り直す) |
| ページの道具 (`app/tool/page`) | 変えない (書き込みは `normalize` を通るので、そのまま `short_title:` が入る) |

### 3.2 `&calendar(show=title)`

- `&calendar` の引数に `show=` を足す。`show=title` のときだけ、セルに出すものを次の順に選ぶ:
  **短いタイトル → タイトル → (どちらも無ければ) 今の目次**。meta を読むだけで、本文は描かない。
  `show=` を書かなければ、今のまま (目次)。知らない値も今のまま。
- **セルのタイトルは、そのページへのリンクにする。** 日の数字より大きな押せる場所になる。
  今も Markdown のページの目次の項目はリンク (見出しへ) なので、セルの中にリンクがあるのは今と同じ。
- **小さい画面とサイドバーは今のまま。** セルには「...」だけを出し、押すとタイトルが浮いて出る
  (今は目次が浮いて出る)。短いタイトルでもスマートフォンの幅のセル (7 等分) には入らないので、
  セルに出すことはしない。CSS と JavaScript は変えない。

### 3.3 `&pages(show=toc)`

`show=` の新しい値 `toc` にする (フラグにしなかったのは、list / date / tree と掛け合わせる組み合わせを
増やさないため。依頼の形は 1 つで足りる)。

```
・2026-11-06（金）カレンダーの手直しと検索の整理   ← ページへのリンク
  ▶ 目次                                            ← 閉じた折りたたみ
・2026-11-05（木）表の並べ替えを試す
  ▶ 目次
```

- 各項目 (`<li>`) は、`show=list` と同じ項目 (既定は `[[title-pagename]]`。`fields=` で変えられる) と、
  その下の `<details class="pages_toc"><summary>目次</summary>…</details>`。中身はツールの「目次」と同じ
  (種別の `summary`。`summarize_link` を立てるので、Wiki のページでも項目は見出しへのリンク)。
- 目次は**種別の `summary` の関数を直に呼ぶ** (`handle()` を通さない)。一覧を開いただけで、
  全部のページが「読んだ」ことにならないように。
- **目次を作るのは種別 wiki と markdown のページだけ。** 作った目次の `section.summary` の直下に `ul` が
  無ければ (見出しが 1 つも無い)、`<details>` ごと出さない。開いても書き出しの 1 文しか出ない
  折りたたみは、押す手間だけ増える。依頼元の日記の「作業なし」の日はこれに当たる (タイトルに「作業なし」と
  出るので足りる)。text・file のページには付けない。
- 読めないページは今の一覧と同じく出ない (`pagelist_apply_rules()` が件数で切る前に落とす)。
- **`&datepages` と `&popularpages` でも使える** (同じ引数を読むので、自然にそうなる)。止める理由が
  無いので止めない。マニュアルは `&pages` に書き、ほかの 2 つは「`&pages` の引数が使える」の既存の
  説明に任せる。テストは `&pages` で行う。
- 文字は `l('Summary')` (日本語「目次」、ツールの名前と同じ)。CSS は `details.pages_toc` にだけ付け、
  最小限にする (押せる形のカーソル、中の箇条書きの字下げ)。テーマのソースを変えるので、
  静的 CSS の再生成と `css-rules.sh` の検査を足す。

### 3.4 重さ

- **区切りは `each=` で行う。** 目次を作るのは、その画面に出す件数だけ (今の作りのまま。`each=31` なら
  1 画面で約 0.45 秒、今のカレンダーより軽い)。依頼元に渡す例にも `each=31` を入れる。
- **`each=` を書かなければ 50 件ずつに区切る (§10)。** 区切らないと全件の目次を作るので、日記の
  ように毎日増える一覧は、年に約 5 秒ずつ遅くなる。Wiki のページの保存も同じだけ遅くなり、何年か後には
  PHP の時間切れ (既定 30 秒) で表示も保存もできなくなる。全部を 1 画面に出したいときは `each=0`。
- **カレンダーは軽くなる。** `show=title` ではタイトルのあるページの本文を描かない (meta を読むだけ)。
- **キャッシュは作らない。** 目次をページごとに保存しておく案は、Wiki の見出しに `&mtime` などの
  関数が書けること、静的エクスポートで URL が変わること、で「古い目次が出る」場合が増える。
  `each=` で足りるうちは足さない。
- マニュアルに「目次の一覧はサイドに置かない」と書く (サイドは全部のページの表示で描かれる)。

### 3.5 マニュアル (ja / en の両方)

- `Wiki/Function/title` — 引数 `short` (例は `&title(short)` を先に書く)
- `Markdown/FrontMatter` — 「短いタイトル」の節。「書いていないものは消えます」に `short_title:` を足す
- `Wiki/Function/calendar` — `show=title`
- `Wiki/Function/pages` — `show=toc`、`each=` の勧め、サイドに置かない
- `Wiki/Function/meta` — `short_title`
- `PageMenu` の「メタ情報」 — 短いタイトルの欄
- `Comparison` (記法の対応表) — 短いタイトルの行
- `CHANGELOG.md`

AI 向けの手順 (`AI.md` / `SKILL.md`) は変えない (書き方を AI に勧めるものではないため)。

## 4. やらないこと

- Markdown の `[PAGES …]` に目次の折りたたみを付けること (今はツリーだけ。依頼は `&pages`)。
- `&pages` の `fields=` に短いタイトルの項目 (`short_title`) を足すこと。
- 既にあるページの meta を、アップグレードで本文から取り直すこと (§6)。
- 目次のキャッシュ (§3.4)。
- §9 の別の問題を直すこと。

## 6. 既にあるサイトへの影響とアップグレード

- データの移し替えは無い。`show=` を書かない限り、カレンダーと `&pages` の見え方は変わらない。
- **既にあるページの `short_title:` は、次に保存したときから効く。** 依頼元が 2026-11-06 以降に
  書いたページは、上げたあとに 1 度保存し直す必要がある (同じ本文で `app/tool/page write … --overwrite`
  でよい。道具は本文が同じでも書く。前の版が履歴に 1 つ増える)。依頼元に知らせるときにこれを書く。
- 古い NextForm で `&title(short){…}` を書くと、`short` が無視されてタイトルになる (§3.1 のとおり、
  先に書けばタイトルは長いほうのまま)。

| `&datepages` と `&popularpages` にも `show=toc` が効く | §2・§3.3 (止めない) |
| `each=` を書かないと年ごとに遅くなり、Wiki のページは保存も遅くなる。カレンダーは最大 42 セル | §2・§3.4・§10 |
| 古い版では `&title(short)` もタイトルになり、後に書いたほうが勝つ | §3.1 (例の順を入れ替えた)・§6 |
| 変換で、タグが無いとフロントマターを出さない。本文に無いときの扱い、引用符・改行 | §3.1 の表 |
| 表示の経路で空文字を立てない、`unset` の場所、並びの値、見出しの判定、`&meta`、CSS の class、未読の印 | §3.1・§3.3 |

確かめて問題が無かったこと:

- `&include`・`&pages(show=contents)`・Markdown の取り込みでは、取り込んだ側のページの配列に書くので、
  取り込まれたページの短いタイトルが外側のページに立つことはない。
- 読めないページは、件数で切る前に一覧から落ちる。タイトルは文字として書く (エスケープされる)。
- 目次を作っても呼び合いにならない (見出しの無いページの書き出しは texts_only で変換し、`&pages` は
  そこで何もしない)。
- 古い版で `show=toc` を書いても、知らない形として list で出る。`&calendar(show=title)` の `show` は捨てられる。

## 9. 調べている途中で見つけた別の問題

いずれもコードを読んで分かったこと。2026-11-07 に利用者が「リスクが低いならすべて直す」と決め、
すべて直した (直し方は [design-review-fixes.md](design-review-fixes.md)、ブランチ `fix/review-findings`)。
`?pages=` の 500 だけは `show=toc` の既定の区切りに関わるので、このブランチで直した。

- **メタ情報の画面で「説明」を空にして保存しても消えない。** `meta_write()` は空のとき
  `unset($page['description'])` とするが、`page_write()` は `$page['description']` が無ければ
  `meta['description']` に触らない。
- **メタ情報の画面でタイトルを消すと、古いタイトルの語が検索の索引に残る。** `meta_write()` が
  `page_write()` の前に `meta['title']` を落としている (`page.inc` の注意書きの「してはいけない」順序)。
- **カレンダーの日のページに読めないものがあると、カレンダーのあるページ全体が 403
  (未ログインならログインの要求) になる。** `page_read()` が読む権限を確かめて止める。
- **週表示の範囲 (`calendar_behind` / `calendar_ahead`) は URL で上限なく指定できる。** 誰でも長い範囲を
  描かせ、日のページの数だけ目次の変換を走らせられる。

実装のあとのレビュー (§12) で見つけたもの:

- **一覧の区切りの `?pages=` に数字でない値を入れると 500 になる** (複製で確かめた)。`pagelist_append()` が
  URL の値をそのまま掛け算に使い、PHP 8.3 では `"abc" * 50` が TypeError になる。`each=` を書いた
  `&pages` と `&datepages` では前から起きていた。`show=toc` は `each=` を書かなくても区切るので、
  ここを通る書き方が増えた。誰でも開ける URL で起きる。
- **`&popularpages` で区切ると「次」のリンクが壊れる** (コードを読んで分かった)。`pagelist_append()` に
  URL の引数とページを渡していないので、いつも 1 画面目で、リンクはサイトのトップを指す。
  `show=toc` では `limit=` に 51 以上を書いたときだけ起きる (既定は 10)。`each=` を書けば前から起きる。
- **Wiki 記法から Markdown への変換で、値を引用符で囲まずにフロントマターに書く** (コードを読んで分かった)。
  両端の `"` `'` は読むときに落ち、`#` で始まる値はよそのツールではコメントになる。題名・タグの
  書き出しと同じ作り。

## 10. 決めたこと (2026-11-07、利用者)

**`&pages(show=toc)` で `each=` を書かなかったときは、50 件ずつに区切る (A)。**

- 書かなくても、1 画面で目次を作るのは 50 ページまで (約 0.7 秒)。一覧の下に「次」「最後」のリンクが出る。
- 全部を 1 画面に出したいときは `each=0` と書く。
- 毎日増える一覧でも、何年経っても遅くならない。

採らなかった案 (B): 区切らない (ほかの形と同じ)。`each=` を書き忘れると、ページが増えるにつれて
表示と保存が遅くなり、いつか時間切れで開けなくなる。

## 11. 実装したあとの確かめ (2026-11-07)

**重さ (実測)。** 日記と同じ形の Markdown (フロントマターに `title:` と `short_title:`、`##` が 10 個、
表と箇条書き) を 365 ページ、複製したサイトに書き、HTTP で 3 回ずつ開いた時間 (秒)。

| 書き方 | 時間 |
|---|---|
| `&pages(..,reverse,type=!file)` (今の一覧) | 0.06 |
| `&pages(..,show=toc,each=31)` | 0.59 |
| `&pages(..,show=toc)` (`each=` を書かない。50 件で区切る) | 0.93 |
| `&pages(..,show=toc,each=0)` (365 件すべて) | 6.6 |
| `&calendar` (今のまま。マスに目次) | 0.64 |
| `&calendar(show=title)` | 0.04 |

§3.4 の見積もり (`each=31` で約 0.45 秒、50 件で約 0.7 秒) より 3 割ほど重い。見積もりは同梱の
CommonMark の変換と DOM だけを測ったもので、実際の目次は Markdown の描き方 (フロントマター・
リンクの解決など) を通るため。全件の meta を読むところ (今の一覧) は 0.06 秒で小さい。
区切れば年数で重くならないことは変わらない。

**アップグレードの手順。** 古い版 (main) で `short_title:` を書いたページを作り、新しい版に上げた。
上げただけでは `meta['short_title']` は無く、同じ本文で `app/tool/page write … --overwrite` を
すると入った (§6 のとおり)。
